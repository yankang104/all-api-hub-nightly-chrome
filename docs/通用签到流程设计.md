# 通用签到流程设计

## 目标

新增站点时，优先通过站点配置完成适配，不再为每个站点复制一套 TypeScript 流程。站点差异拆成三层：

1. 平台能力：接口协议、认证方式、余额读取和默认路由；
2. 页面证据：按钮、已签到状态、成功状态、弹窗和输入框的选择器/文本；
3. 流程编排：按条件执行有限的跳转、点击、填充、等待和断言。

## 当前两个主要平台

### new-api 家族

特点是 `/api/user/*` 协议、cookie 或 user-id 兼容头、余额通常是 quota/usedQuota，签到多为控制台按钮或 `POST /api/user/checkin`。不同白标站点主要差在登录路由、签到页路由和页面选择器，应该共用 `ADAPTER_FAMILIES.NEW_API`，由站点模板提供覆写。

### Sub2API 家族

特点是 `Authorization: Bearer`、`/api/v1/*` 接口、余额通常是美元字段，页面结构与 new-api 不同。它应共用 `ADAPTER_FAMILIES.SUB2API`，不要把 Sub2API 的 token 注入和接口判定散落进通用 DOM 流程。

平台适配器只负责“能力”，不负责某个站点的页面点击。页面动作交给 workflow；VSLLM、Leilei 这类答题/抽奖仍暂时保留为受限复合步骤。

## 本轮已完成的第一阶段

`src/types/workflow.ts` 新增 `if` 步骤和三种安全条件：

- `text`：页面正文命中任一或全部关键词；
- `selector`：页面存在指定元素；
- `path`：当前 pathname 精确或前缀匹配。

`then/else` 分支复用现有 click/fill/wait/assert 执行器，不执行 JavaScript，不引入 eval。保存校验和运行时均限制：

- 总步骤最多 30；
- 条件嵌套最多 4 层；
- navigate 只能位于工作流第一步；
- 所有跳转仍必须同源；
- 条件分支不能包含 navigate；跨页由顶层 stage/context 接续。

这使同一份流程可以表达“已签到则结束，否则按当前平台页面结构点击并检查结果”。

## 自动识别与录制回放的执行边界

`checkin.method = 'auto'` 始终按本站适配/当前页面自主签到；即使保留旧 `workflow`（空记录或缺 `identityPath` 也一样），也不会进入学习路线、不会因为学习元数据不完整而阻止自动签到。
`checkin.method = 'workflow'` 才明确开启回放；保存新学习流程时设置此值。站点编辑可切回自动识别，录制数据保留但停用。旧的 button/api/claim/relogin 和专用站点适配不自动改写。
旧数据兼容：旧版学习流程以 `auto + workflow` 保存且旧运行时会回放。升级后会把「步骤、路线、身份页完整且通过校验」的记录一次性迁为 `workflow`；用户在界面主动切回自动识别时会写入 `workflowReplayDisabled`，迁移不再改回。缺身份页或空步骤的记录保持 `auto`，避免迁过去后引擎在身份闸门停机。
学习路线的身份页要求只属于已启用的回放，自动签到仍遵守其现有登录/账号核验逻辑。配置错误独立诊断，不再把登录成功后的“学习路线缺少身份页”说成“登录状态已失效”。

## 学习模式：手动签到一次即学会路线

用户的目标不是「录下几个点击」，而是**学会网址**：手动完成一次签到后，扩展记住这次经过的同源页面路线，之后自动沿这条路线到达签到页再执行动作，不再要求用户手填签到页地址。

每个站点只有一个学习入口「学习本站流程」（融合学习，`kind='both'`），为通用能力、不针对单个站点：一次演示里先手动登录、再完成一次签到，同时产出两份产物 ——

- **登录配置**：录下用户演示的登录入口、用户名字段、密码字段、提交动作或 OAuth 动作，生成可安全回放的登录配置；
- **签到流程**：录下签到路线与签到动作，生成 `route + identityPath + steps`。

底层仍保留 `LearningKind='login' | 'checkin'` 两种旧会话语义：界面不再提供单独入口，但升级前已开始的旧会话仍可正常结束与保存。

- 开始学习必须收到顶层采集器就绪回执；SPA 地址在隔离世界轮询并在动作前补采。事件串行读改写，结束学习先 `FLUSH_LEARNING` 等最后一笔证据落盘，再编译保存。读回比较完整动作与滚动字段（忽略对象键顺序，保留数组顺序），不再只比步骤数量。
- 内层滚动面板记录为 `scrollContainer` CSS 选择器，动作仍用 `scrollIntoView`；回放目标尚未挂载时，在该面板内有界逐屏查找。旧记录没有面板信息时才扫描可见滚动面板和整页，绝不回放固定像素距离。

### 登录产物（LearningKind='login'，旧入口兼容）

- 采集事件只有选择器与「是否输入过值」标记（`fieldRole: 'username' | 'password'`），**绝不保存账号、密码、OTP、token 或任何输入值**；点击事件标注 `loginAction: 'entry' | 'submit' | 'oauth'`。
- 稳定选择器优先：`data-testid` → 手写 `id` → `name` → `aria-label` → 短可见文本；拒绝自动生成 id（`base-ui-_r_h_`、`:r1:`、`radix-*`、UUID 等），候选必须经回放侧同一解析器验证唯一命中。
- 文字选择器的学习与回放统一使用 `innerText` 并折叠空白，不把 SVG 的 `title/desc` 拼入按钮文案；按钮/链接的 `text=` 候选当场零命中也拒绝保存。旧版已保存的「图标标题 + 按钮文案」仅在完整匹配、去掉 SVG 元数据后恰好等于可见文案、且候选唯一时兼容，不泛化匹配隐藏 HTML 文案、不猜测其它 OAuth 提供商。
- 保存前过校验、保存后读回逐字段核对；重新学习会清掉旧的入口/OAuth 配置，不遗留互相矛盾的字段。

### 签到产物（LearningKind='checkin' / 融合学习的签到部分）

载体是 `CheckinWorkflowConfig`：

```ts
export interface CheckinWorkflowConfig {
  steps: CheckinWorkflowStep[];
  /** 同源 pathname[#hash]，按访问顺序；最后一项是执行 steps 的目标页 */
  route?: string[];
  /** 签到前用于核对当前登录账号的身份核验页；必须是学习路线中的同源页面（可与签到目标同址） */
  identityPath?: string;
}
```

规则：

- 终点动作必须真的像签到：既无成功/已完成证据、又命中导航/资料词（或链接指向别的页面）的最后一个点击不会被当成签到动作，保存侧直接报「没录到签到动作」—— 当天已签到（按钮已变成「已签到」）时也不会保存出一份回放必然找不到按钮的流程；带明确成功/已完成证据的动作不受此限。
- 保存前过滤：只收同源路径（`pathname + hash`，不含 origin 和 query），外域一律丢弃；
- 只去**连续**重复项，用户中途回到同一页要保留，因为那可能是真实路线的一段；
- 最后一项固定为「记录到有效签到点击的页面」，若点击页不在路线里则追加，保证「末项 = 目标页」；
- `identityPath` 是**身份核验页**：站点形态不同，它可能是一个独立的个人资料页，也可能就是签到页本身（卡片式签到站点把账号和签到按钮放在同一页）。推断顺序：用户点击过的资料入口 → 路线中签到目标之前的强资料路径（以资料词收尾的页面优先）→ **兜底：签到终点页自己**。无论哪种形态，它必须是学习路线中的同源页面；偏好 / 财务 / 安全类页面（`/settings`、`/account/billing` 等）**任何来源都不会被推断成身份页** —— 它们看不到登录账号，推错会让回放每次都在错误页面等身份而停机。与签到终点同址时，引擎到页后先核对账号、再执行签到动作，读不到可核对的账号就停机；
- `route` 非空时，导航由 `route` 承载，`steps` 里不再放 `navigate` 步骤，避免双跳和校验器「navigate 只能第一步」的冲突；
- `route` 为空或未定义时，完全退回只执行 `steps` 的老行为，手写工作流不受影响。

执行侧：`runCheckinWorkflow` **按路线逐页回放** —— 在当前页先执行属于该页的 `if(path)` 动作块，再进入下一页；不再先跳到终点而跳过中间页的点击。会卸载文档的中间页点击之前必须落盘任务阶段，导航后交回引擎核验身份。终点页的签到动作仍在身份核验之后执行。

- 根路径或已知业务页（如 `/dashboard/overview`）即使被配置为 `loginUrl`，也不能因此从学习路线里删除；明确的登录/认证路径仍排除。
- 不能只跳末项：用户手动签到经过的中间页常常是必经的（先进控制台、再进签到页），深链接直达终点会被站点重定向回首页，表现是反复跳同一页直到放弃。
- 整条路线**先整体解析再推进**：只要有一项跨站或非法就整条拒绝，不能走到那一页才发现 —— 那时已经跳出过站点了。
- 收敛性由两层保证：推进只向后、不回退重走；同一地址的重复跳转由引擎既有的「同一个签到页最多跳 2 次」计数兜住（引擎为自己的 navigate 统一写该标记，路线导航走的也是这条通道）。
- 比较时忽略查询串：`/check-in?tab=1` 与路线里的 `/check-in` 视为同一页。

### 回放闭环：登录 → 身份核验（独立资料页或签到页本身）→ 错号重登 → 签到

1. 必要时登录（沿用现有会话或按学习到的登录配置登录）；
2. 沿 `route` 前进，到 `identityPath`**核验身份**（给 SPA 渲染时间，读接口与页面旁证）；身份页与签到终点同址（卡片式签到站点）时，就是到终点后**先核验、再点击**；
3. 只有**明确错号**才退出并重新登录（重新登录后旧核验标记失效，必须再次经过身份核验）；
4. 身份**未知**时不下结论：不清 Cookie、不自动切号、不盲签 —— 停机交给用户确认；
5. 到签到终点后执行学习的签到动作，并读页面证据判定成功/已完成/未知。

引擎侧配套约束（`automation/engine/engine.ts` 与 `automation/learning/workflow.ts`）：

- 学习路线站点在登录返回页（verify / verify-oauth / 表单提交后）**不提前读取或绑定身份**，身份基准只能来自身份核验页，避免把错误会话提前写成基准；
- 「身份已核验」标记跨页保存，但必须**晚于最近一次会话重建**才有效：切换账号、受管 GitHub 重授权、自动重试重登、token 清号、退出后重登（relogin）之后旧标记一律失效，重登后必须重新核验；
- 路外导航预算（`MAX_ROUTE_OFF_PAGE_NAVIGATIONS`）只在当前页仍不在学习路线上时生效，防止误伤「成功回到身份页后的正常前进」；
- 签到终点反复被重定向回来时，返回身份页同样受跳转预算限制，用尽后停机（不降级绕过核验）；
- 路线缺少身份核验页的配置不允许降级盲签；
- 签到跳转计数键为 `pathname + search + hash`：两边都带 hash 时按 hash 区分（hash 路由站点的 `/#/profile` 与 `/#/check-in` 各自计数，不会把第 3 跳误判成「重复跳转」），任一边不带 hash 时按 pathname 折叠（站点重定向到 hash 子路由时护栏仍生效）；写入格式与 `workflow.ts` 的「尝试进入 pathname+hash」一致，路外预算成对计数才能配对。
- 轮换令牌站点（`authBootstrap`）：新版 new-api 分叉把登录态做成「会话 cookie 换短命 Bearer 令牌」，令牌只留在页面内存里 —— 扩展默认的 cookie + user-id 请求头在这类站点上一律 401，余额、签到前后的快照、身份全都读不到（一梦五千年 fapi.leileihog.top 实测）。配了 `authBootstrap.endpoint` 后，读余额与身份之前先用会话 cookie 换一枚同类型令牌再去请求；引导**只允许同源**（跨域一律拒绝，绝不把会话 cookie 发出去），令牌只在本轮内存复用（每站点 60 秒最多换一次），不落盘。
- 余额读取顺序：同源兼容端点（new-api / sub2api）→ 站点显式配置的**跨域接口**（`identitySource.endpoint` 响应里的 `points`，符号按站点货币「积分」展示）→ 页面可见文本；跨域路径与身份核对共用同一份配置与同一道安全门（只读 GET、仅 https、本站域名的自身/父/子域），任何一步读不到只降级，绝不停机。手动刷新的页面注入同样带这条路径（响应原样 base64 带回、background 解码）。

安全边界不变：只记录同源、限长的选择器、可见标签和有限成功/已完成词；绝不记录 input value、密码、token、cookie、localStorage、请求头；只有 `frameId === 0` 且 runId/origin 匹配的事件才被接受。

## 后续迁移顺序

### 阶段一：继续扩展安全 DSL

在 `types/workflow.ts` 增加有限的 `retry`（固定次数）、`assert-api`（同源只读接口、字段路径和期望值）以及 `capture`（保存受限页面证据）。每个步骤必须有固定上限，禁止 while、任意表达式和用户脚本。`workflow-validation.ts` 与 `automation/workflow.ts` 同批修改，并为每个步骤增加 RED/GREEN 测试。

### 阶段二：抽出平台能力接口

新增 `src/automation/platform-adapters.ts` 或 `src/lib/platform-capabilities.ts`，定义：

- `resolveEndpoints(site)`；
- `buildAuthHeaders(account, site)`；
- `readIdentity(response)`；
- `readBalance(response)`；
- `readCheckinEvidence(response)`。

将 `headless-checkin.ts`、`balance.ts`、`identity.ts` 中按家族分支迁入 new-api、Sub2API、VoAPI 等适配器。`engine.ts` 只负责登录、身份闸门、stage 和 workflow 生命周期；`checkin.ts` 只负责通用证据收敛，不再增加站点 if/else。

### 阶段三：站点配置和 UI

`SiteTemplate` 只保存平台引用、登录入口、签到页、选择器、判定词和 workflow JSON。`SiteModal` 增加条件步骤的结构化编辑器或模板片段，普通用户不必手写 JSON；高级模式保留 JSON。`site-probe.ts` 负责识别平台，不能直接决定某个站点的特殊流程。

## 专用流程边界

- `relogin`：保留为通用受控动作，因为它涉及 Cookie 清理、余额基线和跨页 stage；
- `claim`：可逐步迁移为 workflow 的 fill + submit + assert；
- `VSLLM` / `Leilei`：先保留复合步骤，等答题、翻牌、抽奖状态模型稳定后再拆成受限动作节点；
- 任何需要验证码、可信指针、OpenCV 或跨上下文协调的能力，不塞进 DSL，继续由 automation/background hook 提供。
